# 検索式自動調整（#97）の実 API 評価: 所見

実施日 2026-09-12。設計と限界は [評価計画](query-optimization-bench-plan.md)、
再現手順は [experiments/query-optimization-bench/README.md](../experiments/query-optimization-bench/README.md)。

**これは 3 ケース・シード分割 1 通り・1 反復の後ろ向き探索的評価**であり、新規レビューでの性能や
専門家検索への非劣性を示すものではない。下の数値は「現在の PubMed に作成日上限を適用した」条件で測った。

## 実行条件

- モデル: `gemini-3.5-flash`（GeminiProvider 既定）
- `maxHits` = 10,000（アプリ既定 `HIT_THRESHOLD`）、`maxIterations` = 5 — **事前固定し、gold を見て変えていない**
- シード = 各ケース 3 群（凍結）、held-out = 残りの全研究
- 日付条件: `datetype=crdt` の上限を各レビューの検索日に設定（式には書かず、esearch のパラメータで付与）

## 第 2 条件: `maxHits` = 1,000（**事後探索 / post-hoc**）

上の結果を見たあとで追加した条件であり、事前登録した `default`（10,000）とは**主張の強さが違う**。
条件は `PROFILES` にコードで登録し、CLI から任意の数値を渡せないようにしてある（gold を見て目標を
調整できないようにするため）。

| ケース | 条件 | hits | held-out 再現率 | 研究当たりレコード | 停止 | 反復 |
|---|---|---:|---:|---:|---|---:|
| R1 | C0 | 277 | 15/15 = 1.000 | 15.4 | — | — |
| | C1 | 277 | 1.000 | 15.4 | achieved / conditions_met | 1 |
| R2 | C0 | 12,844 | 46/54 = 0.852 | 267.6 | — | — |
| | C1 | **11,958** | 0.852 | 244.0 | **needs_review / iteration_limit** | 5 |
| R3 | C0 | 4,718 | 11/15 = 0.733 | 337.0 | — | — |
| | C1 | **1,526** | **0.667** | 117.4 | **needs_review / iteration_limit** | 5 |

### 6. 目標が実際に効く水準なら、自動調整は動く。ただし未知の研究を落とす

R3 は 4,718 → **1,526 件（−67.7%）** まで削った。R2 は 12,844 → 11,958（−6.9%）。
`default` 条件では 3 例とも無変更だったので、**あの no-op は目標値が緩すぎたことが原因**と確認できた。

しかし両ケースとも `outcome` は `tradeoff` である。

- R3: **czerny 2000 を取りこぼした**（held-out 再現率 0.733 → 0.667）
- R2: miki 1969 を失い lestradet 1981 を拾った（再現率は 0.852 で同じ、中身が入れ替わった）

自動調整が守るのは**与えられたシードだけ**で、未知の適格研究は保護対象に入っていない。
件数を削れば削るほど、この取りこぼしは起きやすくなる。**目標を締めるなら、同時に
「削った語が何を落とすか」を見る仕組みが要る**（現在は語の寄与を AI に渡すだけで、採用判定には入らない）。

なお 5 反復を使い切っても両ケースとも目標 1,000 件には届かなかった（11,958 / 1,526、いずれも `iteration_limit`）。

### 7. ドラフトの実測値が run ごとに大きくぶれる（条件間比較は成立しない）

同じ入力・同じモデル（`gemini-3.5-flash`、temperature は skill 既定）で、C0 の件数が次のように変わった。

| ケース | `default` 実行の C0 | `tight-1000` 実行の C0 | 比 |
|---|---:|---:|---:|
| R1 | 380 | 277 | 0.73 |
| R2 | 16,409 | 12,844 | 0.78 |
| R3 | 1,595 | 4,718 | **2.96** |

R3 では held-out 再現率も 0.800 → 0.733 と変わっている。したがって
**2 つの条件の差を `maxHits` の効果として読むことはできない**（C0 が別物なので）。
有効なのは**各条件の中での C0 → C1 の対比較**だけである。

この振れ幅は、1 レビュー 1 反復という今回の設計では分離できない。
条件の効果を主張したいなら、同一 C0 を両条件に与える（ドラフトを凍結して再利用する）設計が要る。

## 所見

### 1. 既定の `maxHits` では、自動調整が起動しても何もしない（R1・R3）

R1 は 380 件・シード 3/3 捕捉、R3 は 1,595 件・3/3 捕捉。いずれも「シードを捕捉済み」かつ
「件数が上限 10,000 以下」で**初回評価の時点で条件を満たす**ため、AI は改善案を 1 件も出さずに終了した
（R1 の 3 試行の内訳は 初期計測 → MeSH 文脈の取得 → 再検証）。

`maxHits` の既定 10,000 は、PubMed で実務的に絞れた式（数百〜数千件）に対して**目標として緩すぎる**。

### 2. `achieved`（条件達成）は網羅性を意味しない — 実測で確認された（R3）

R3 は条件達成で停止したが、held-out の**20%（12/15）しか捕捉できていない**。
未捕捉は clagett 1995・ranaboldo 1997・bochicchio 2015。
「既知シードを全部捕捉し、件数上限も満たした」状態と「未知の適格研究を取りこぼしていない」状態は別物であり、
画面表示でも報告でもこれを同一視してはいけない。

### 3. 改善余地がある局面ほど、採用規則が改善を捨てる（R2）

R2 は 3 ケース中唯一「条件未達」だった（シード 913749 が未捕捉、16,409 件が上限超過）。
AI は候補を 2 つ提案したが、両方とも却下された。

| 候補 | 変更 | hits | シード捕捉 | 判定 |
|---|---|---:|---|---|
| candidate-2 | ブロック 2 から `Diabetic Retinopathy[Mesh]` を削除 | 16,409 → **4,500** | 変化なし | 却下 |
| candidate-3 | ブロック 3 から汎用語 5 件（`association*` `associate*` `development` `course` `history`）を削除 | 16,409 → 11,987 | 変化なし | 却下 |

`isImprovement`（[queryOptimizationService.ts](../src/app/services/queryOptimizationService.ts)）は
**シードが 1 件でも未捕捉のうちは「捕捉シード数が増えたか」しか見ない**。そのため
**件数を 73% 削る候補が「改善なし」と判定され**、2 回連続の非改善で `no_improvement` 停止となった。

「シードも取れていないし件数も多すぎる」という*最も改善が必要な局面*で、2 つの目的のうち片方が
評価対象から外れる。ここまでを見た時点では「採用判定を 2 次元にすべき」と考えたが、
**却下候補を gold で実測した結果、その結論は誤りだった**（次項）。

### 3-2. 却下は保護的だった — シード捕捉は再現率の代理にならない

却下された 2 候補を、C0 と同じ分母・同じ日付条件で実測した（`npm run eval:candidates`）。

| 候補 | hits | held-out 再現率 | 失った held-out 研究 |
|---|---:|---:|---|
| C0 | 16,409 | 0.963（52/54） | — |
| candidate-2 | 4,500（−73%） | **0.796** | **9 件**: ballard 1986, bojestig 1998, burditt 1968, hardin 1956, miki 1969, rodriguez-villalobos 2005, rudnisky 2017, teuscher 1988, zavrelova 2011 |
| candidate-3 | 11,987（−27%） | 0.907 | 3 件: hardin 1956, mccance 1989, miki 1969 |

**採用判定を「シード捕捉を減らさずに件数が減れば採用」に緩めていれば、candidate-2 が採用され、
54 研究中 9 件を失っていた。** 却下は結果的に正しかった。

本質的な問題は採用規則ではなく、**シード捕捉が再現率の代理として弱すぎる**ことである。
両候補とも**シード 3 件の捕捉はまったく変わらないまま**、未知の適格研究を 3〜9 件落としている。
3 件のシードでは 17 ポイントの再現率低下を検出できない。
第 2 条件（`maxHits` = 1,000）で提案が採用され、R3 が czerny 2000 を失ったのも同じ構造である。

### 4. 取りこぼしは古い文献に偏る

未捕捉だった研究は R2 が dwyer 1985・pambianco 2006、R3 が clagett 1995・ranaboldo 1997・bochicchio 2015。
R2 で捕捉できなかったシード 913749 も 1977 年の記録である。
抄録が無い・MeSH 付与が現在と異なる古い記録に対して、ドラフトの語彙が効いていない。

### 5. 語別計測の予算が、最も難しいケースで先に尽きる（R2）

R2 は語別計測が 100 通信の上限に達し、`未測定` のまま AI に渡っている。
ブロックが大きいケースほど語数が多く、寄与の情報が無い状態で改善案を出すことになる。

## #97 への提案（優先順）

1. **採用判定を「シード捕捉を減らさずに件数が減れば採用」に緩めてはいけない。** 実測では、
   その規則で採用されたはずの候補が held-out を 9/54 失っていた（所見 3-2）。
   必要なのは緩和ではなく、**削除が何を落とすかの見積もり**である:
   - 語の固有寄与（既に計測している）が大きい語の削除を採用判定で抑制する
   - MeSH 主要語のような「ブロックの背骨」にあたる語の削除は、件数削減幅にかかわらず別扱いにする
   - シードが 3 件では保護として弱い。`#/expand` の margin 判定で得た研究を保護集合に足す、
     シードを増やすよう促す等、**守る側の集合を厚くする**
2. **`maxHits` の既定値を見直す。ただし締めるだけでは害が出る。** 固定の 10,000 は緩すぎて no-op を招くが、
   1,000 に締めた第 2 条件では 2 ケースとも **held-out を落とすか入れ替える** `tradeoff` になった。
   相対目標（初期式の実測に対する比率）に変えると同時に、**削除が何を落とすかを採用判定に入れる**こと
   （語の固有寄与が大きい語の削除を抑制する、削除候補の影響を明示する等）。締める仕組みと守る仕組みは対で要る
3. **`achieved` の表示を変える。** 「既知シードを全部捕捉し件数上限を満たした」であって網羅性の保証ではない、
   と画面と保存記録の両方に明記する（R3 は条件達成で 20% 取りこぼした）
4. **語別計測の予算配分。** 上限に達したら「未測定」を AI に伝えるだけでなく、
   大きいブロックから優先して測る・反復間で測り直さない等で実効的な情報量を上げる
5. **古い文献への対策**を検討する（抄録なし記録に効く語・MeSH の年代差を考慮した提案）

## この評価が答えていないこと

- **Q3（人手検索との比較）は未回答。** B1 の再構成が未完成
- 3 ケース・固定シード 1 分割・条件ごとに 1 反復。**ドラフトの振れ幅が大きい**（所見 7。R3 で 2.96 倍）ため、
  2 条件の差を `maxHits` の効果として読むことはできない。条件内の C0 → C1 の対比較だけが有効
- `maxHits` = 1,000 の条件は結果を見てから追加した**事後探索**であり、事前登録した条件と同じ強さでは主張できない
- 入力は完成レビューの Methods（選考後の改訂を含む）。学習混入も排除できない
- 分母は PMID のある既知組入研究に限る。R1 で 3 件、R2 で 2 件、R3 で 3 件が PMID 無しで分母の外
- `hits` は検索結果の件数であって、人の選考時間でもレビューの結論の正しさでもない
