- **Q-B（調整ロジック）**: 同じ C0 から出発したとき、新しい調整ロジックは旧ロジックより安全か（有害採用）・何を得て何を失うか

## 2. 3 つの層

### 層 A: 通し比較（Q-A）

各版がそれぞれの初期式生成で C0 を作り、そのまま自分の調整ロジックで C1 まで進める。版ごとに C0 が違うので
**対比較ではなく分布の比較**として読む。

- 新版: 層 B の新版 run のうち、新版の生成器で凍結した C0 から出発したもの（C0 は現行の `generateDraftFormula` の出力そのもの）をそのまま使う
- 旧版: 旧版ハーネスで C0 をその場生成（`live`）して C1 まで回す。旧版ハーネスは criteria-only しか持たないため、**層 A は criteria-only だけ**で比べる

### 層 B: 凍結 C0 の対比較（Q-B）

新版の生成器で凍結した同じ C0・同じシード分割・同じ `maxHits` = 2,000・`maxIterations` = 5 を、旧ロジックと新ロジックに与える。
差は調整ロジックとハーネスの違いだけになる（LLM の出力のぶれは残る）。

### 層 C: 模擬レビュアーによる再調整（Q-C）

新版だけで行う（旧版には外側の確認も保護再調整も無い。これが改定で足した機能そのもの）。
層 B の新版 run の後に、§4 の模擬レビュアーを置いて最大 2 ラウンド再調整する。
**ループ無しの新版（層 B）とループ込みの新版を両方報告**し、ループの寄与を分ける。

## 3. ケース

### 開発用（既存）

R1 マインドフルネス禁煙 / R2 増殖糖尿病網膜症の予後因子 / R3 血管手術の出血減少薬。#106 の設計はこの 3 件を見て作ったので、
ここでの改善は一般化の根拠にしない。

### 確認用（新規 3 件・結果を見る前に凍結）

[Cochrane-bench](https://github.com/youkiti/Cochrane-bench) の cc-by gold 62 件から、[評価計画 §1](query-optimization-bench-plan.md) と同じ事前基準で機械的に選ぶ。

1. R1〜R3 と、§1 で却下済みの 4 件（PMC10164701 / PMC5865125 / PMC11384553 / PMC11110109）を除く
2. 基準を満たす候補を、却下理由（どの基準で落ちたか）付きで全件記録する
3. 候補が 3 件を超えたら、乱数 20260915 で 3 件を選ぶ（出版年やテーマで事後に選び直さない）。3 件に満たなければ満たした件数で進め、基準は緩めない
4. gold 監査（群の構築・共有 PMID の目視判定）とシード凍結を、**どの版の run よりも前に**済ませ、`role: 'confirmation'` として登録する

**結果が悪いことを理由に差し替えない。** B1（Cochrane 元検索式の再構成）は今回も対象外。

## 4. 模擬レビュアーの仕様（層 C）

製品の「include した文献を保護して再調整する」と同じ操作を、人の代わりに gold で答える。

- **判定の対象**: 最終レビューで人に見せる候補。外側の確認の候補と、保留した試行の失う集合から書誌を出した分（`impact.inspected`）
- **判定規則**: 候補の PMID がケースの gold（検索日内・シード以外）のどれかの研究の報告なら include、それ以外は exclude。maybe は使わない
- **再調整**: include が 1 件以上あれば、そのラウンドの最良式を初期式にし、include をシードに足し、同じ `maxHits` / `maxIterations` で新しい run を始める（製品の保護再調整と同じ入力。`bootstrapOptimization.test.ts` の「include 保護再調整」を参照）
- **停止**: 新しい include が 0 件、または 2 ラウンドに達したら止める
- **gold の境界**: gold は判定の返答にだけ使う。拡張語の生成・候補の取得・AI の候補選定・調整ループの入力には渡さない（既存の `confirmationAudit` の境界と同じ）

**この規則は保守的に偏る**: gold に無い適格研究も exclude と答えるため、実際の人より include が少ない。
逆に、人が include を見逃すことは模擬しない。

## 5. 規模

| 軸 | 値 |
|---|---|
| ケース | 開発 3 + 確認 3 = 6 |
| C0 の入力 | criteria-only / seeded |
| C0 のドラフト | 条件ごとに 3（新版の生成器で、実行 SHA で新規に凍結。既存の draft1 / draft2 は #132 の修正前の生成なので使わない） |
| シード分割 | 既定 `s20260912` + 追加 `s20260915`（`eval:prepare -- --seed 20260915`） |

seeded の C0 はシードを入力に使うので分割ごとに作る。1 ケースあたり C0 は criteria-only 3 + seeded 3 × 2 = 9、
run は criteria-only 3 × 2 分割 + seeded 6 = 12。

| 層 | run 数 |
|---|---:|
| B 旧ロジック | 6 × 12 = 72 |
| B 新ロジック（= A の新版を兼ねる） | 72 |
| A 旧版の通し（criteria-only・live 3 回 × 2 分割） | 6 × 6 = 36 |
| C 再調整ラウンド（include が出た run だけ・最大 2） | 0〜144 |
| **合計** | **約 180〜324** |

見積もり（既存 run の実測: 1 run あたり LLM $0.01〜0.08・1.5〜3 分・NCBI 約 110〜150 回）:
**LLM 費用 $15〜25、直列実行で 10〜15 時間**。C0 の凍結（1 ケース 9 個 × 6 ケース = 54 個。1 個あたり LLM 3N 回程度）と確認用ケースの準備は別枠で、LLM 費用は数ドル。

## 6. 指標（事前固定）

採点は**全層で同じ採点規則**を使う（C0 / C1 の指標は `f84762e` から変わっていない `metrics.ts` で計算し、旧版に無い有害採用の監査だけを新版ハーネスで後から計算する。§8 W1・W2）。
分母・日付条件・研究単位の採点は [評価計画 §3-2〜§4](query-optimization-bench-plan.md) のまま。

### 主要

1. **最終式の held-out 再現率**（研究単位）と **hits**
   - 層 A: ケース × 版ごとの分布（最小・中央値・最大）
   - 層 B: C0 ごとの差（新 − 旧）。失った研究・得た研究を実名で
2. **有害採用数**（採用直前の式に対して held-out を 1 件でも失った採用。`adoptionAudit`）

### 副次

3. **取りこぼしの回収**（層 C）: C0 が取りこぼした held-out 研究のうち、(a) 確認候補に提示された研究、(b) 再調整後の最終式に捕捉された研究。研究名つき
4. **提示されなかった held-out の再現率**: 模擬レビュアーに一度も見せていない held-out だけを分母にした再現率。include をシードに足すと、その研究は式が必ず捕捉するようになる。回収とは別に、式そのものの一般化を見るための指標
5. **「条件達成なのに取りこぼしあり」の件数**と、そのとき最終レビューの外側の確認・削除影響の確認が「確認済み」以外（判定待ち・未達・判定済み（残件あり））を示したか
6. **確認負担**: 1 ラウンドあたりの提示件数、模擬レビュアーの判定件数、ラウンド数
7. **費用**: NCBI 通信数、LLM 呼び出し数と費用、所要時間
8. **C0 の品質**（層 A）: 構文エラー率、C0 の hits と held-out 再現率

## 7. 判定の基準（結果を見る前に固定）

形成的評価であり統計的な検定はしない。そのうえで、次を満たすかをケースごとに報告する。

| 基準 | 内容 |
|---|---|
| S1 安全 | 新ロジックの有害採用が全 run で 0。旧ロジックで有害採用が出た C0 について、新ロジックが同じ種類の候補を保留または却下している |
| S2 劣化なし | 層 B で新ロジックの最終式が旧ロジックより held-out を多く失った組を全件実名で調べ、原因を「調整ロジック」「LLM 提案のぶれ」「その他」に分類する。**調整ロジック起因が 0** |
| S3 通しで良くなった | 層 A の criteria-only で、新版の最終式の held-out 再現率の中央値が旧版以上のケースが過半数。件数（hits）の中央値も併記し、再現率だけで良否を言わない |
| S4 取りこぼしを回収できる | 層 C で、C0 が取りこぼした held-out 研究の少なくとも 1 件が最終式に回収されたケースが、開発用・確認用のそれぞれに 1 件以上ある |
| S5 誤った安心を出さない | 「条件達成なのに取りこぼしあり」の run で、最終レビューが外側の確認を「確認済み」と表示した割合を報告する（候補 0 件で確認済みになる仕様は #151 で残した既知の挙動なので、件数を明示する） |

- S1・S2 を満たさなければ、再現率が上がっていても「うまくいくようになった」とは結論しない
- 開発用で満たし確認用で満たさない基準は、「開発ケースへの適合の可能性」として分けて書く
- `maxHits` = 2,000 は変えない。gold の成績を見てプロファイル・判定規則・ケースを変えない。事後に足す条件は `postHoc` として別に報告する

## 8. 実装作業（commander に回す）

評価ハーネス（`experiments/`）への追加が主で、製品コード（`src/`）は変えない。

| # | 作業 | 内容 |
|---|---|---|
| W1 | 旧版パッチ | `f84762e` から評価専用ブランチ `bench/legacy-f84762e` を切り（master へはマージしない）、旧 `run.ts` に凍結 C0 の読み込み（sha256 検証）・シード分割指定・`maxHits` 2,000 のプロファイル・ラベルを足す。C0 / C1 の指標は旧版の run 内で計算する（`metrics.ts` は `f84762e` から変わっていないため、新版と同じ採点になる） |
| W2 | 旧版の有害採用の採点 | 旧版ハーネスには有害採用の監査が無いため、新版ハーネスの `eval:score-legacy` で旧版の `run.json` に対して監査だけを計算し、`scored.json` に保存する |
| W3 | 模擬レビュアー | `eval:optimize` に `--oracle-rounds <n>` を足す。§4 の規則でラウンドごとに `run.json` の `oracle` と `oracle-round-<k>.json` を保存する。途中のラウンドからは再開せず、失敗した run は基本 run からやり直す |
| W4 | 確認用ケース | 62 件の機械的な選定スクリプト（却下理由の全件記録）→ `eval:prepare` でのケース登録（`role: 'confirmation'`）→ gold 監査の手動確認 |
| W5 | バッチと集計 | §5 の行列を 1 プロセス直列で回すドライバ（1 run ごとに永続化・完了済みはスキップ・0 件や失敗も 1 行ログ）と、層 A / B / C の表と S1〜S5 を出す集計 |

W1 と W4 は独立に並行できる。W2 → W3 → W5 の順に依存する。

## 9. 実行の手順

1. **準備**（実 API を使わない）: W1〜W5 のマージ、全コマンドの `--dry-run`
2. **ケースの凍結**: 確認用 3 件を選定・監査・シード凍結し、選定記録をコミットする。**ここまでは run の結果を一切見ない**
3. **C0 の凍結**: 新版の実行 SHA で、6 ケース × 条件 × 分割の C0 を凍結してコミットする。構文エラーで凍結できない生成は、別番号で作り直した回数も記録する
4. **パイロット**: R3 の 1 C0 について、旧ロジック・新ロジック・再調整ループ・旧版の通しを 1 本ずつ流し、採点・集計まで通ることと 1 run の実費を確かめる。§5 の見積もりから大きく外れたら、ここで止めて相談する
5. **本実行**: §5 の行列を直列で回す。NCBI キーあり。**他の実 API ジョブ・E2E と同時に走らせない**（#131 の 429 と、負荷下の E2E の偶発失敗を避ける）。途中で落ちたら未完了分だけ再実行する
6. **報告**: `docs/query-optimization-rerun-findings.md` に結果と S1〜S5 の判定を書き、#106 にリンクする

## 10. この計画で答えられないこと

- 3 + 3 ケース・2 分割・各 3 ドラフトの後ろ向き評価であり、新しいレビューでの性能や専門家の検索への非劣性は示さない
- 模擬レビュアーは gold に無い適格研究を exclude と答えるので、実際の人より回収が少なく出うる。人が見落とすことは模擬しない
- 旧版は評価用パッチを当てたうえでの再現で、当時のハーネスそのものではない。層 A の旧版は criteria-only だけ
- 入力が完成レビューの Methods であること、LLM の学習混入、現在の索引を使うことは [評価計画 §7](query-optimization-bench-plan.md) のまま残る
- ブロックの自動承認は人の承認を省いている（影響の向きは不明）
