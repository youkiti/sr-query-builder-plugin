# プロトコル → AI による検索式 の改善ループ 計画

作成日: 2026-10-05（同日改訂: 主目標を全捕捉優先へ変更、実験を段階制に、試験群は最終版で一度だけ。同日追記: 原著式が 0 件のレビューを対象外に）　状態: 第 2 段階（改善ループ）を反復 5 で打ち切り（最良は v4）。試験群は未使用（経過は [log.md](log.md)）

## 0. 目的と問い

本拡張の「研究プロトコル → AI による PubMed 検索式の作成」を、ベンチマーク上の実測で繰り返し改善する。対象は**シード論文なし**で、適格基準だけから式を作る段階（製品でいう `#/protocol` → `#/blocks` → `#/draft` の初期式）。シードを使う自動調整（[query-optimization-bench](../query-optimization-bench/README.md)）は対象外とする。

目指す式は「**組み入れ研究を取りこぼさず、そのうえで件数が少ない**」もの。

問い:

1. 現行の作り方（手順書と道具）で Haiku が作る式は、どれだけのレビューで組み入れ研究を全件捕捉でき、そのとき件数はどの程度か。Cochrane 原著の検索式と比べてどうか。
2. 手順書・進め方・道具をどう変えると良くなるか。その改善は、開発に使っていないレビューでも再現するか。
3. 再現した改善は、製品の生成経路（既定モデルは Gemini）へ移しても効くか。

## 1. 決定事項（2026-10-05）

| 項目 | 決定 |
|---|---|
| 主目標 | 全捕捉を優先し、同じなら件数が少ない方を良いとする。再現率の低下を適合率の上昇で埋め合わせない（§2-2） |
| 拾うべき文献 | 最終組み入れ研究。研究単位（関連論文が 1 本でも拾えれば捕捉）で判定し、論文単位の値も併記する |
| F7 | 参考値として表に残す。β=7 の根拠は Kataoka et al. 2023（[Res Synth Methods, doi:10.1002/jrsm.1649](https://doi.org/10.1002/jrsm.1649)） |
| 式を作る主体 | Claude Code の Haiku サブエージェント。指揮役（このリポジトリで作業する Claude）が起動し、手順書と測定コマンドを渡す |
| データ | Cochrane-bench の検索・スクリーニング用データ。CC BY 50 件 + CC BY-NC 203 件 = 253 レビュー（2026-10-05 にローカルの `reviews.jsonl` の行数で確認）。評価可能な正解集合を持ち、原著式の件数が 0 件でない 251 件を対象にする（§2-1） |
| 実験の大きさ | 段階制（§5-1） |
| 試験群 | 最終版で一度だけ開ける。最終評価へ進むかどうかは、必ず人に確認してから決める。不十分と判断されたら改善ループへ戻る（§7） |
| 公開リポジトリに置くもの | 計画・手順書・スクリプト・分割規則・集計値のみ。レビュー由来の本文、PMID 一覧、レビュー単位の結果は置かない |
| ベンチの場所 | 環境変数 `COCHRANE_BENCH_DIR` で渡す。パスをファイルに書かない（Cochrane-bench は後日公開予定） |

## 2. 指標

### 2-1. 正解集合と測り方

レビュー 1 件・式 1 本について、ベンチと同じ条件（PubMed 登録日 `edat` が 1800-01-01 〜 そのレビューの MEDLINE 最終検索日）で測る。

**評価可能な正解集合**は、最終組み入れ研究の報告のうち、PMID があり、かつ上の日付条件のもとで PubMed から取得できるものとする。検索日より後に登録された報告は分母に入れない（入れると全捕捉が原理的に達成できなくなる）。評価可能な報告が 1 本も無い研究は分母から外し、評価可能な研究が 1 つも無いレビューは対象から外す。

あわせて、ベンチの記録で原著式の件数が 0 件のレビューも対象から外す（原著式の PubMed 翻訳が結果を返しておらず、原著式と比べられないため）。外すのは分割のあとで、他のレビューの群の割り当ては変えない。

この絞り込みは最初から適用する。本計画の数字は、断りのない限りすべて評価可能な正解集合で数えたものである。253 レビューでの内訳（2026-10-05 実測、ベンチのコミット `36c17b5`）:

| | レビュー | 外した報告 | 外した研究 | 評価可能な研究が無いレビュー | 原著式が 0 件のレビュー | 残るレビュー |
|---|---|---|---|---|---|---|
| CC BY | 50 | 12 | 8 | 0 | 0 | 50 |
| CC BY-NC | 203 | 65 | 49 | 1 | 1 | 201 |
| 計 | 253 | 77 | 57 | 1 | 1 | **251** |

外した報告はすべて「検索日より後に登録」で、PubMed に存在しない PMID は無かった。

| 指標 | 定義 |
|---|---|
| 件数 | 式の総ヒット数 |
| 再現率（研究単位） | 評価可能な組み入れ研究のうち、報告が 1 本でも捕捉された研究の割合 |
| 全捕捉 | 再現率（研究単位）が 100% であること |
| 取りこぼし研究数 | 捕捉できなかった評価可能な組み入れ研究の数 |
| 再現率（論文単位） | 評価可能な組み入れ報告のうち捕捉された割合。併記用 |
| 適合率 | 捕捉した組み入れ報告の数 ÷ 件数 |
| F7 | 50·P·R ÷ (49·P + R)。R は研究単位。参考値 |

式が構文エラー・0 件・未提出のときは再現率 0・全捕捉できずとして数え、分母から外さない。同じレビューで複数回生成したときは、先にレビュー内で平均する。

### 2-2. 版の良し悪しの比べ方

次の順に見る。上の項目で悪くなった版は、下の項目が良くても採らない。

1. **全捕捉できたレビューの割合**
2. **平均再現率（研究単位）と取りこぼし研究数の合計**
3. **件数**（両方の版が全捕捉できたレビューどうしで比べる。全レビューでの件数の中央値も併記）

全捕捉できなかったレビューは「目標未達」として数える。経過は 1 と 2 で追い、未達を適合率や F7 の上昇で相殺しない。

F7 を主指標にしない理由: 検索式の適合率は通常 2% を下回り、この領域では F7 ≈ 50·P となって再現率にほとんど反応しない（P=0.5%・R=1.00 で 0.201、P=1.0%・R=0.50 で 0.253）。根拠論文でも、F7 で順位付けした最上位の分類器は外部検証で F7 0.4036 に対し再現率 0.2352 だった（同論文の抄録）。

### 2-3. 基準線

| 名前 | 中身 | 用途 |
|---|---|---|
| 原著式 | ベンチが保持する、Cochrane 原著の MEDLINE 検索式の PubMed 翻訳（件数と再現率はベンチに記録済み） | 専門家が作った式の水準。到達目標の目安 |
| v0 | 製品の現行プロンプトをそのまま手順書にしたもの | 改善の出発点 |
| 製品経路 | 製品の生成コードを既定モデルで動かしたもの | 持ち帰り時の確認（§8） |

原著式でも全捕捉は簡単ではない。評価可能な正解集合で数えると（2026-10-05 実測）、研究単位で全捕捉できているのは 251 件中 123 件（49%。CC BY 31/50、CC BY-NC 92/201）、論文単位では 101 件（40%）。翻訳の不確かさと、原著が他のデータベースで見つけた研究を含むためである。絞り込み前の数え方では 253 件中 112 件・87 件だった。目標値は第 1 段階の実測後に固定した（2026-10-05）: 検証群で、全捕捉の割合と平均再現率（研究単位）が原著式を下回らないこと。件数は、両方が全捕捉できたレビューで原著式の 2 倍以内を目安とする。

### 2-4. ベンチ上の全捕捉が意味しないこと

ベンチで全捕捉できた式が、未知のレビューで取りこぼさない保証にはならない。組み入れ研究が少ないレビュー（3 研究以下が 253 件中 25 件。この数だけは絞り込み前の研究数で数えている）では全捕捉が偶然でも起きる。組み入れ研究数の多寡別の内訳を必ず見る（§6）。

## 3. データと分割

### 3-1. 使うもの

`COCHRANE_BENCH_DIR` 配下の、ティア別の検索・スクリーニング用データから次を読む。

- レビューごとの検索日、組み入れ PMID と研究の対応、原著式の件数と再現率
- プロトコル本文（題・目的・適格基準）。検索方法・検索式・結果の節は入力に含めない（既存ハーネスの `buildProtocol` と同じ方針）

RIS（抄録つき）と、全文評価で除外された文献のラベルは使わない。

### 3-2. 分割

レビュー ID と固定の塩から決定的に 3 群へ分ける。一覧をコミットしなくても同じ分割を再現できるよう、規則だけをコードに置く。ティアで層別する。

| 群 | 割合 | 件数（対象 251 件。2026-10-05 実測） | 使い方 |
|---|---|---|---|
| 開発 | 20% | 53 | 式・失敗例を読んでよい。変更案はここから作る |
| 検証 | 30% | 74 | 集計値だけを見る。個々の式や失敗例は読まない。採否の判定に使う |
| 試験 | 50% | 124 | 最終評価で一度だけ測る |

- 既存ハーネスで開発に使った 4 件（r1 / r2 / r3 / c1）は、割り当てに関わらず開発群へ固定する
- 同じレビューの更新版が別の群に分かれないよう、Cochrane ID から版の接尾辞を除いたものを分割のキーにする。現在の 253 件に同一 ID の重複は無い（2026-10-05 実測）が、検査はコードに残す。主題が近いだけの別レビューは検査していない
- 開発群から「動作確認用 5 件」と「固定小集合 20 件」を、領域・レビュー種別・組み入れ研究数が偏らないよう層別して最初に 1 回だけ抽出し、凍結する

## 4. 改善の対象

`harness/` に置く。版ごとにタグを付け、結果には必ず版タグを記録する。

| 対象 | 中身 | 変更の例 |
|---|---|---|
| 手順書（プロンプト） | Haiku に渡す作業手順。v0 は製品の現行スキル（`blockDesigner` / `meshSuggester` / `freewordDesigner` / `filterDesigner`）のプロンプトから起こす | AND で必須にする概念の選び方、同義語の展開、フィルタを付ける条件 |
| 進め方（プロセス） | 作業の順序と工程 | 概念整理 → 用語生成 → 検査の順序、独立した見直し工程、複数候補の統合 |
| 道具・予算 | Haiku が実行できるコマンドと回数の上限 | MeSH 辞書の照会、ブロック別の件数、ヒット文献の題の標本、修正回数の上限 |

**予算を増やす効果と、手順を変える効果は別の実験で測る。** 1 つの実験で両方を動かさない。

道具は製品が実際にできることの範囲に揃える。出力は `search_formula.md` 互換（`#N` 行と結合行）で、構文と括弧の検査を通ったものだけを提出として受け付ける。

### 4-1. 生成条件（第 0 段階で固定し、結果に記録する）

- モデル: Haiku 4.5（`claude-haiku-4-5-20251001`）。エイリアスは使わない
- 温度などの生成設定: サブエージェントの既定。変えられない設定は「既定」と記録する
- 入力範囲: §3-1 のプロトコル本文と手順書だけ
- 測定回数・修正回数の上限、1 回の生成あたりの費用の上限
- 最終候補の選び方: Haiku が最後に提出した 1 本。複数の候補を採点結果で選び直すことはしない

### 4-2. Haiku に見せないもの

- 組み入れ PMID、再現率、適合率、F7、原著式。採点は指揮役が別プロセスで行い、結果を Haiku に返さない
- Web 検索、PubMed への直接アクセス。PubMed へは道具経由のみ
- 他のレビューの結果、過去の版の式

## 5. 実験の進め方

### 5-1. 段階制

1 回の実験は「変更案 1 つを、同じレビュー群で変更前と比べる」こと。

| 段階 | レビュー数 × 生成回数（1 版あたり） | 用途 |
|---|---|---|
| 動作確認 | 5 件 × 1 回 | 構文・通信・出力形式の確認 |
| 通常の改善実験 | 固定小集合 20 件 × 2 回 | 改善候補の選別 |
| 有望な候補 | 開発群 53 件 × 2 回 | 小集合だけの改善でないかの確認 |
| 採否判定 | 検証群 74 件 × 2 回 | 凍結した候補と変更前の比較 |
| 最終評価 | 試験群 124 件 × 3 回 | 最終版と基準版の性能・安定性 |

- 独立した評価単位はレビューである。20 件 × 2 回は 40 件のベンチではなく、20 レビューの評価
- 件数は基準線のばらつきを見て第 1 段階で調整する。レビュー間の差が大きければレビュー数を、同じレビューで生成が不安定なら回数を増やす
- 検証群での件数と「検出したい最小の改善幅」は、第 1 段階の終わりに固定した（2026-10-05）: 検証群 74 件 × 2 回、平均再現率（研究単位）で +0.08。結果が出てから件数を足して有意にする運用はしない

### 5-2. 1 反復の流れ

1. **分類**: 開発群の失敗を分類する（§6）
2. **仮説**: 分類に対して、一般化できる変更を 1 つ選ぶ。1 反復で動かす要因は 1 つ
3. **変更**: 手順書・進め方・道具のいずれかを直し、版タグを上げる
4. **通常の改善実験**: 固定小集合で変更前と比べる。良くなった式・悪くなった式を読み、仮説どおりの理由で動いたかを確かめる。偶然の改善は採らない
5. **有望なら開発群全体**で確かめる
6. **残ったら版を凍結して検証群**で判定する
7. **記録**: `log.md` に仮説・変更点・各段階の集計値・採否と理由を 1 反復 1 項目で残す。不採用も残す

### 5-3. 採否規則（実行前に固定）

検証群で、変更前との対比較により判定する。

**悪化していないこと（すべて必須）**

- 全捕捉できたレビューの割合が下がらない
- 平均再現率（研究単位）が下がらず、取りこぼし研究数の合計が増えない
- 失敗率（構文エラー・0 件・未提出）が上がらない

**改善していること（どちらか）**

- 再現率の改善: 平均再現率（研究単位）の差の 95% 信頼区間（レビュー単位のブートストラップ）の下限が 0 を上回る
- 件数の改善: 再現率側が上の「悪化していない」を満たしたうえで、両方の版が全捕捉できたレビューでの件数の比の 95% 信頼区間の上限が 1 を下回る

加えて、CC BY と CC BY-NC で差の向きが一致すること。

開発群で良く、検証群で満たさない変更は捨てる。検証群の結果を見て同じ変更を直し、再度検証群に当てることは 1 回までとする。

### 5-4. 終了条件

次のどれかで改善ループを止め、人への確認（§7 第 4 段階）へ進む。第 1 段階の終わりに見直して固定した（2026-10-05。最後の 1 項を追加）。

- 採用した変更が 3 つ
- 反復が 10 回
- 検証群に出した候補が 5 つ
- 5 反復続けて不採用
- 検証群で目標値（§2-3）に達した

## 6. ベンチに合わせ込まないための規則

- **手順書に固有の語を書かない**: 特定の疾患名・薬剤名・MeSH 見出し・PMID・レビュー題を、例示を含めて手順書に入れない。例が要るときはベンチに無い題材で書く。開発群の本文と手順書の語の重なりを機械的に検査する
- **変更は一般原則として書く**: 「このレビューでは〜」ではなく「〜のような基準のときは〜」。採用する変更には、裏付けとなる開発群のレビューを 3 件以上・2 領域以上挙げる
- **失敗は分類してから直す**: 個別の式ではなく分類に対して手を打つ。分類の初期案 — 概念ブロックの過剰（AND の増やしすぎ）／ブロックの不足／MeSH の誤り・過剰な限定／フリーワードの不足（同義語・綴り・語尾）／フィルタによる取りこぼし／構文エラー／件数の過大
- **検証群は数字だけ**: 個票を読むと、検証群が第二の開発群になる
- **試験群は一度だけ**: 開けるのは最終評価の 1 回。開けた日時・版・結果を `log.md` に残す
- **内訳を見る**: レビューグループ（領域）別、レビュー種別（介入・診断精度・予後など）別、組み入れ研究数の多寡別。一部の層だけで稼いだ改善は採用理由に明記する
- **記憶による漏れを見る**: Cochrane レビューは公開文献で、モデルが原著の検索式を覚えている可能性がある。検索日が新しいレビューと古いレビューで結果を比べ、偏りがあれば報告に書く
- **道具は製品でできる範囲に限る**: ベンチでしか得られない情報（組み入れ研究の有無など）を返す道具を足さない

## 7. 段階と完了条件

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0. 土台 | 分割規則、評価可能な正解集合の確定、プロトコル組み立て、採点、道具のコマンド、結果の保存形式、生成条件の固定。`.gitignore` にレビュー単位の入出力を追加 | 単体テストが通る。原著式の件数・再現率をベンチ記録から再計算し、ベンチの集計値と一致する。動作確認（5 件 × 1 回）が通る |
| 1. 基準線 | 原著式の各指標を対象の全 251 件で算出（ベンチ記録から。通信なし）。v0 を開発群全体 × 3 回で実行 | 原著式と v0 の全捕捉割合・再現率・件数・失敗率の表。生成の揺れの大きさ。検証群の件数・検出したい最小の改善幅・終了条件・目標値を一度だけ固定して記録 |
| 2. 改善ループ | §5-2 を回す | §5-4 の終了条件 |
| 3. 持ち帰り | 採用した変更を製品のプロンプト・制御へ移し、製品経路で確かめる（§8） | 製品経路での開発群・検証群の結果と PR |
| 4. 人への確認 | 検証群までの結果（基準線・原著式との比較、内訳、採用・不採用の一覧）を示し、最終評価へ進むかを人が決める | 「進む」または「不十分」の判断を記録。不十分なら第 2 段階へ戻り、終了条件を数え直す |
| 5. 最終評価 | 最終版と基準版（v0、製品の変更前）を試験群で 1 回だけ測る | 報告書。結果を見たあとの手直しはしない |

第 4 段階を飛ばして試験群を開けない。第 5 段階のあとにさらに改善を続ける場合、その後の試験群の数字は「確認」として報告できない。

## 8. 製品への持ち帰り

Haiku サブエージェントは自分で測って直せるが、製品の生成経路は決まった順に 1 問 1 答で進む。手順書で効いた変更が製品で効くとは限らないため、次の順で確認する。

1. 変更を「プロンプトの文言」「生成の順序・制御」「追加の測定」に分け、製品のどこへ入れるかを決める
2. 製品の生成コードに実装する（複数ファイルになるので commander の手順で委譲・レビューする）
3. 製品経路を既定モデルで動かし、固定小集合で変更前後を比べる。停止理由や失敗率など、主指標以外の挙動の変化も前後で比べる
4. 検証群で §5-3 の採否規則に当てる

## 9. 実行上の規約

- **通信**: NCBI への呼び出しは数千回になる。1 件ごとに保存し、再開は未処理分だけにする。結果は「成功／正当な 0 件／失敗／不明」を区別し、失敗を 0 件に畳まない。レート上限は同時に走る全プロセスの合計で守る（並列 N なら各自に上限 ÷ N）
- **並列**: Haiku サブエージェントは同時に数件まで。並列数は測定コマンド側の上限とあわせて決める
- **採点スクリプト**: 数値を報告する前にコードレビューを通す
- **数値の出し方**: 版タグ、分割、レビュー件数、生成回数、測定日を数値と一緒に示す。取得件数をベンチの件数と突き合わせる
- **キー**: `.env` から読み、ログ・結果・コマンドラインに出さない
- **PubMed の変化**: 索引は日々変わる。対比較する 2 つの版はなるべく同じ日に測る。日付をまたいでも先に測った版は測り直さず、測定日を対比較のレポートに残す（2026-10-05 改訂。当初は「同じ日に測るか、古い版を測り直す」）

## 10. フォルダ構成（予定）

```
experiments/protocol-to-formula-loop/
├── plan.md        # この文書
├── log.md         # 反復の記録（集計値のみ）
├── harness/       # 手順書・進め方・道具の定義（版タグつき）
├── src/           # 分割・プロトコル組み立て・道具・採点・集計
├── reports/       # 段階ごとの集計表（ティア別・分割別。レビュー単位の行は置かない）
├── cases/         # ベンチから組み立てた入力（gitignore）
└── results/       # レビュー単位の式・測定・ログ（gitignore）
```

NCBI の測定と PMID 捕捉は既存ハーネスの `ncbiEval.ts` を再利用する。日付条件はベンチに合わせて `edat` を使う（既存ハーネスは `crdt`）。

## 11. 解釈の限界

- 組み入れ研究は原著レビューが見つけたものに限られる。原著が見落とした適格研究を拾っても適合率は上がらない
- PMID を持たない組み入れ研究、検索日より後に登録された報告は分母に入らない
- 現在の PubMed で測るため、検索日当時の索引は再現できない
- ベンチ上の全捕捉は、未知のレビューで取りこぼさない保証ではない（§2-4）
- Cochrane レビューに偏る（介入研究・RCT が多い）。他の種類のレビューへの一般化は別に確かめる必要がある
- Haiku サブエージェントでの結果は、製品の既定モデルでの結果を保証しない（§8 で確認する）
