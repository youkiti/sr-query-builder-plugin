# プロトコル → AI による検索式 の改善ループ 第 5 ラウンド計画（Gemini 3.8 Flash・推論 high を、Opus の 1 本と同じ条件で動かす）

作成日: 2026-10-08　状態: **計画**（未実行）

[plan-round4.md](plan-round4.md) の続き。第 4 ラウンドは、固定小集合 20 件で Opus 5.5 の 1 本（v1o）が平均再現率 0.948 だったところで終了した。ここに書いていないこと（指標、分割、ベンチに合わせ込まないための規則、実行上の規約）は [plan.md](plan.md) のままとする。経過は [log.md](log.md) に「第 5 ラウンド」として続けて書く。

このラウンドは改善ループの反復ではなく、手順書を変えずにモデルだけを替える確認である（第 1 ラウンドのあとの Gemini 3.5 Flash Lite の確認、第 4 ラウンドと同じ位置づけ）。反復の回数には数えず、採否の判定もしない。

## 0. 出発点

固定小集合 20 件での、これまでの 1 本と 3 本束ねの成績（[log.md](log.md) 第 4 ラウンド）。

| モデル | 1 本の平均再現率 | 3 本束ね | 1 本の全捕捉 | 1 本の取りこぼし研究数 |
|---|---|---|---|---|
| Haiku 4.5（v1 → v4） | 0.771 | 0.859 | 35.0% | 415.2 |
| Haiku 5.5（v1h → v4h） | 0.860 | 0.907 | 45.0% | 289.8 |
| Sonnet 5.5・medium（v1s → v4s） | 0.905 | 0.934 | 55.0% | 203.7 |
| Opus 5.5・medium（v1o → v4o） | 0.948 | 0.965 | 61.7% | 137 |

- 第 4 ラウンドでは、3 本束ねるかどうかより、どのモデルで作るかのほうが大きく効いた。
- Gemini は、製品の既定モデルである 3.5 Flash Lite しか試していない（開発群・検証群。推論の強さは指定なし）。Flash の上位の版で、推論を強くしたときの成績は分かっていない。
- Gemini 3.8 Flash は Opus より単価が安い。Opus の 1 本に近い成績が出るなら、製品で選べるモデルの候補になる。

## 1. 決定事項（2026-10-08、依頼者の決定）

| 項目 | 決定 |
|---|---|
| 問い | Gemini 3.8 Flash（推論 high）の 1 本は、Opus 5.5（medium）の 1 本にどこまで近いか |
| モデル | `gemini-3.8-flash`。エイリアスは使わない（2026-10-08 に Gemini API のモデル一覧で、この ID があり、推論に対応していることを確かめた） |
| 推論の強さ | high |

## 2. 問い

1. **主な問い**: Gemini 3.8 Flash・high の 1 本は、Opus の 1 本（v1o）と比べて、再現率・全捕捉・取りこぼし・件数がどれだけ違うか。
2. **束ねたとき**: 3 本束ねると 1 本からどれだけ上がるか。束ねた式は、Opus の 1 本・Opus の 3 本束ねと比べてどうか。
3. **位置づけ**: Sonnet の 1 本（v1s）、Haiku 5.5 の 3 本束ね（v4h）、Gemini 3.5 Flash Lite の 1 本（v1g）と並べたとき、どこに入るか。保存済みの結果と並べるだけで、追加の生成は要らない。
4. **費用**: 推論 high で、1 本あたりのトークン数（推論のトークンを含む）と所要時間がどれだけになるか。

## 3. 条件

| | Opus（第 4 ラウンド、保存済み） | Gemini 3.8 Flash（このラウンド） |
|---|---|---|
| 1 本の版 | v1o | v1g38h |
| 束ねた版 | v4o | v4g38h（v1g38h の 3 本を OR） |
| モデル | `claude-opus-5-5` | `gemini-3.8-flash` |
| 推論の強さ | medium | high |
| 手順書 | v1 と同じ本文 | 同じ |
| 道具と上限 | 測定 20 回、提出 4 回 | 同じ |
| 実行 | 20 件 × 3 本 = 60 | 60 |
| 道具の渡し方 | Claude Code のサブエージェントがシェルから呼ぶ | API の関数呼び出し（`geminiRun.ts`。v1g と同じ） |
| 打ち切り | 道具の上限だけ | 道具の上限に加え、モデルの呼び出しは 1 本あたり 60 回まで |

**そろえること**

- 手順書の本文（`---` 以降）が v1 と一字一句同じであること。道具の読み替えの節（`geminiRun.ts` の設定の節）は v1g のときと同じ文面のまま使い、変えない。
- 60 本すべてが、指定したモデルと推論の強さで動いたことを、実行の記録で確かめる（応答の `modelVersion`、送った要求の推論の指定、推論のトークン数が 0 でないこと）。確かめられない実行は採点に入れず、作り直す。
- v1g38h と v4g38h は同じ日に採点する。

**そろえられないこと**（結果の記録に毎回書く）

- **道具の渡し方が違う。** Opus はサブエージェントがシェルとファイルで作業し、Gemini は API の関数呼び出しで作業する（プロトコルは最初のメッセージに入り、式は専用の関数で書く。手順書の末尾に読み替えの説明が数行付く）。モデルの違いと、この違いは切り分けられない。v1g のときと同じ制約である。
- **推論の強さが違う**（Opus は medium、Gemini は high）。会社が違うので、同じ名前でも同じ量の推論ではない。「同じ強さにそろえた比較」ではなく、「この設定どうしの比較」として読む。
- **採点の日**。v1o の採点は 2026-10-08（UTC）。このラウンドの採点が別の日になっても、v1o は測り直さない（plan.md §9）。日付を記録する。
- Gemini 3.5 Flash Lite（v1g）は推論の強さを指定しておらず、採点は 2026-10-05 と 10-07 である。

## 4. 比べ方

数え方は第 4 ラウンド（plan-round4.md §4）と同じにする。

- 1 本の成績は、レビューごとに 3 本の成績を平均した値。3 本束ねは、同じ 3 本を OR で束ねた式 1 つ。
- 見る指標は、全捕捉できたレビューの割合、平均再現率（研究単位）と取りこぼし研究数（差の 95% 信頼区間はレビュー単位のブートストラップ）、件数（比の中央値、1 万件・5 万件を超えた数）。
- 失敗した実行（未提出・構文エラー・0 件・呼び出し 60 回で打ち切り）は、再現率 0 として数え、分母から外さない。

**出す比較**（すべて固定小集合 20 件。差は「右 − 左」）

| 比較 | 目的 |
|---|---|
| v1o → v1g38h | 主な問い。1 本どうし |
| v1g38h → v4g38h | 束ねる上積み |
| v4o → v4g38h | 3 本束ねどうし |
| v1o → v4g38h | Gemini を 3 本束ねると、Opus の 1 本に届くか |
| v1s → v1g38h、v4h → v1g38h | 位置づけ |
| v1g → v1g38h | Flash Lite（推論の指定なし）からの伸び。v1g は保存済みの採点の最初の 3 本を固定小集合で集計し直す。測り直しが要るなら、この行は出さない |

**あわせて記録するもの**

- 同じレビューの 3 本のあいだの、再現率の標準偏差と、件数の最大 ÷ 最小（`p2f:spread`）。
- 取りこぼしの原因の内訳、概念あたりの MeSH・フリーワードの語数、概念が 1 個だけの実行の数（`p2f:diagnose`）。
- 費用: 1 本あたりの入力・出力・推論のトークン数、応答の回数、所要時間、道具の呼び出し回数。中央値と最大値。金額は実行した日の料金表から別に計算する（この計画には単価を書かない）。
- 再試行の回数と、打ち切り・エラーで終わった実行の数。
- ティア別（CC BY 5 件・CC BY-NC 15 件）と、検索日の新旧別の値。

## 5. 結果の読み方（実行前に固定）

採否の判定はしない。次の区分で読み、結果を見たあとで区分の線を動かさない。小さい実験の運用上の基準で、統計的な確証とは区別する。

**主な問い: Opus の 1 本との差**（v1g38h − v1o の平均再現率）

| 区分 | 条件 | 読み方 |
|---|---|---|
| Opus の 1 本に並ぶ | 差が −0.03 より大きく、信頼区間が 0 をまたぐ | 単価の安い候補として、開発群全体で確かめる価値がある |
| Opus の 1 本を下回る | 差が −0.03 以下で、信頼区間の上限が 0 を下回る | この設定では Opus の代わりにならない。Sonnet・Haiku 5.5 とのどちらに近いかを書く |
| Opus の 1 本を上回る | 差が +0.03 以上で、信頼区間の下限が 0 を上回る | 道具の渡し方の違いを含めて、開発群全体で確かめる |
| どちらとも言えない | 上のどれでもない | 20 件 × 3 本では決められない。広げるかを依頼者に確認する |

0.03 は第 4 ラウンドと同じ線である。

**束ねる上積み**（v4g38h − v1g38h）は、plan-round4.md §5 の 3 区分（束ねる価値がある／1 本で足りる可能性がある／どちらとも言えない）をそのまま使う。

**件数**は、区分とは別に、v1o に対する件数の比の中央値と、1 万件・5 万件を超えた実行の数を必ず書く。再現率が並んでも、件数が 2 倍を超えていれば、そのことを区分の横に書く。

**このラウンドの結果で決めないこと**

- 製品の既定モデル。固定小集合 20 件は、手順書の選別に繰り返し使った集合である。
- 「推論を強くすると良くなる」かどうか。このラウンドは high の 1 点だけで、同じモデルの推論なし・low とは比べていない。

## 6. 進め方

1. **実行役に推論の強さを渡せるようにする**（コードの変更）。いまの `geminiRun.ts` は生成の設定を何も送っていないので、このままでは high を指定できない。
   - `conditions.json` に推論の強さの項目を足し、検証する（`conditions.ts`）。項目が無い版（v1g・v4g）の要求は、これまでと 1 バイトも変えない。
   - 項目がある版では、要求に推論の指定を足す。
   - 推論のトークン数と、送った推論の指定を、実行ごとの記録（`agent.json`）に残す。いまは応答ごとのログにしか無く、合計に入っていない。
   - 関数呼び出しの応答に付く推論の署名を、次の要求にそのまま返していることをテストで固定する（いまの実装は応答の内容を丸ごと返している）。
   - 実装は commander に乗せ、レビューを通してからマージする。
2. **版を用意する**: `harness/` に v1g38h（手順書は v1 の写し。`conditions.json` にモデルと推論の強さ）と v4g38h（`combine.from: v1g38h`、`k: 3`）を置く。手順書の語の重なり検査を通す。
3. **動作確認**: 動作確認用 5 件のうち 1 件 × 1 本を、別のフォルダで動かす。次を確かめる。この 1 本は採点に入れない。
   - 応答の `modelVersion` が `gemini-3.8-flash` であること、推論のトークン数が 0 でないこと。
   - 提出まで到達すること。署名まわりのエラー（HTTP 400）が出ないこと。
   - 1 回の応答が、要求の制限時間（120 秒）に収まること。収まらなければ、本番の前に制限時間を延ばす。
   - 1 本あたりのトークン数。見積もり（§7）の 3 倍を超えたら、本番の前に依頼者へ知らせる。
4. **本番の生成**: `p2f:gemini` で `--version v1g38h --subset fixed --runs-per-review 3`。並行数は 4。NCBI のレートは 1 プロセスの中で守られる（plan.md §9）。ほかの実 API の計測や E2E と同時に流さない。落ちたら同じコマンドで続きから流す（済んだ実行は飛ばし、エラーの実行だけ作り直す）。作り直した数を記録する。
5. **束ねる・採点する**: `p2f:combine` で v4g38h を作り、`p2f:score` で 2 つの版を同じ日に採点する。生成した実行の数（60）と採点できた数、束ねた式の数（20）を突き合わせる。
6. **比べる**: §4 の表の組を `p2f:compare` で出す（実行数の違う組は `--candidate-runs-per-review`）。`p2f:diagnose` と `p2f:spread` を v1g38h に、`p2f:spread` を v4g38h にかける。
7. **記録する**: log.md に「第 5 ラウンド」として、§3 の条件、§4 の表、§5 の区分、費用、読み方の注意を書く。reports/ には集計値だけを置く（レビュー単位の行、式、PMID は置かない）。

モデルや推論の強さが指定どおりでなかった実行、通信の障害で道具が動かなかった実行だけを作り直す。打ち切り・未提出は作り直さず、失敗として数える。

集計のコードを足したり直したりする場合は、数値を報告する前にコードレビューを通す（plan.md §9）。

目安は、Gemini 3.5 Flash Lite の実績（1 本あたり入力 約 3.4 万・出力 約 1,000）をそのまま当てた下限である。推論 high でどれだけ増えるかは、動作確認の 1 本で初めて分かる。推論のトークンは出力として課金される。

## 8. このラウンドで分かること・分からないこと

- 分かるのは、固定小集合 20 件・v1 の手順での、Gemini 3.8 Flash（high）の 1 本と 3 本束ねの成績・件数・費用と、Opus の同じ本数との差の大きさである。
- 差には、モデルの違い、推論の強さの違い、道具の渡し方の違いが混ざる。どれが効いたかは分けられない。
- 20 件 × 3 本では、差の信頼区間は広い（第 4 ラウンドの Sonnet と Opus の 1 本どうしで、+0.043 に対して 0.013〜0.081）。「どちらとも言えない」になる可能性を見込んでおく。
- 推論の強さを変えたとき（指定なし・low・medium）や、Gemini の上位の版（Pro）は分からない。
- 手順書 v1 は Haiku 4.5 の失敗を見て作ったものである。Gemini 向けに直せば結果は変わりうる。
- 固定小集合は開発群の一部で、Cochrane レビューに偏る。開発群全体・検証群で同じ大きさになるかは分からない。
