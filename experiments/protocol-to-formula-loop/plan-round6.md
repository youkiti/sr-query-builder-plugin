## 2. 問い

1. **主な問い**: Qwen3.8 27B・GLM-5.3 のそれぞれで、1 本の成績は Gemini 3.8 Flash・high の 1 本（v1g38h）とどれだけ違うか。再現率・全捕捉・取りこぼし・件数で見る。
2. **束ねたとき**: 3 本を束ねると 1 本からどれだけ上がり、件数は何倍になるか。束ねた式は Gemini 3.8 Flash の 1 本・3 本束ねと比べてどうか。
3. **位置づけ**: Haiku 5.5・Sonnet・Opus の 1 本と 3 本束ねの表のどこに入るか。保存済みの結果と並べるだけで、追加の生成は要らない。
4. **道具を使う作業が成り立つか**: 関数呼び出しを最大 60 回続ける作業で、提出まで到達する実行の割合。関数の引数が壊れた応答、空の応答、打ち切りの数。これまでのモデルではほぼ 0 だったが、ここでは結果の一部として読む。
5. **費用**: 1 本あたりのトークン数（推論を含む）、所要時間、金額。

**そろえること**

- 手順書の本文（`---` 以降）が v1 と一字一句同じであること。
- 道具の読み替えの節（`geminiRun.ts` の「この作業の設定」）は、Gemini のときと同じ文面を使う。実行役が違っても、モデルに見える指示は同じにする。
- 最初のメッセージ（プロトコルの渡し方）、関数の名前・引数・説明、1 回の応答で 1 つだけ実行する扱い、空の応答が 2 回続いたら終える扱い、呼び出し 60 回の打ち切りを、`geminiRun.ts` と同じにする。
- 温度などの生成設定は指定しない（Gemini と同じ）。送るのは推論の強さだけにする。
- 120 本すべてが、指定したモデル・提供元・推論の強さで動いたことを、実行の記録で確かめる（応答の `model` と `provider`、送った推論の指定、推論のトークン数が 0 でないこと）。確かめられない実行は採点に入れず、作り直す。
- 2 つのモデルは同じ日に生成し、4 つの版（v1q27・v4q27・v1glm・v4glm）を同じ日に採点する。

**そろえられないこと**（結果の記録に毎回書く）

- **推論の強さは、同じ名前でも同じ量ではない。** OpenRouter の `high` が、それぞれのモデルでどれだけの推論になるかは、モデルと提供元が決める。「同じ強さにそろえた比較」ではなく、「この設定どうしの比較」として読む。推論のトークン数を必ず並べる。
- **API の形式が違う。** Gemini は Google の形式、こちらは OpenAI 互換の形式で、関数の定義の書き方と、結果の返し方が違う。モデルの違いと切り分けられない。
- **GLM-5.3 は提供元によって量子化が違う**（fp4・fp8・不明が混在し、単価も 30 倍近く開く）。1 社に固定し、ほかへ黙って切り替わらないようにする。結果は「その提供元・その量子化の GLM-5.3」の成績であり、ほかの提供元や手元で動かした場合と同じとは限らない。
- **2 つのモデルは量子化が違う。** Qwen3.8 27B は量子化なし（bf16）、GLM-5.3 は fp8 で動かす。どちらも OpenRouter の表示による値で、提供元の中で実際に何が動いているかは外から確かめられない。
- **2 つのモデルは大きさが違う。** Qwen3.8 27B は小型のモデルで、Qwen の公開版で最大のもの（2.4T-A95B）ではない。「Qwen の上限」ではなく「小型の公開モデルでどこまでできるか」として読む。
- **採点の日。** v1o の採点は 2026-10-08（UTC）。v1g38h は第 5 ラウンドの採点日。このラウンドが別の日になっても測り直さない（plan.md §9）。日付を記録する。
- Opus・Sonnet・Haiku はサブエージェントがシェルとファイルで作業した。道具の渡し方が違う（第 5 ラウンドと同じ制約）。

## 4. 比べ方

数え方は第 4・第 5 ラウンドと同じにする（plan-round4.md §4）。

- 1 本の成績は、レビューごとに 3 本の成績を平均した値。3 本束ねは、同じ 3 本を OR で束ねた式 1 つ。
- 見る指標は、全捕捉できたレビューの割合、平均再現率（研究単位）と取りこぼし研究数（差の 95% 信頼区間はレビュー単位のブートストラップ）、件数（比の中央値、1 万件・5 万件を超えた数）。
- 失敗した実行（未提出・構文エラー・0 件・呼び出し 60 回で打ち切り・関数の引数が壊れて進めなかった実行）は、再現率 0 として数え、分母から外さない。

**出す比較**（すべて固定小集合 20 件。差は「右 − 左」。モデルごとに出す。下は Qwen の例で、GLM も同じ組を出す）

| 比較 | 目的 |
|---|---|
| v1g38h → v1q27 | 主な問い。1 本どうし |
| v1q27 → v4q27 | 束ねる上積み |
| v4g38h → v4q27 | 3 本束ねどうし |
| v1g38h → v4q27 | 3 本束ねると、Gemini 3.8 Flash の 1 本に届くか |
| v1h → v1q27、v1s → v1q27、v1o → v1q27 | 位置づけ |
| v1q27 → v1glm、v4q27 → v4glm | 2 つの公開モデルどうし |

第 5 ラウンドの本番が終わっていない場合、v1g38h・v4g38h との比較は、その採点が済んでから出す。それ以外の比較は先に出せる。

**あわせて記録するもの**

- 同じレビューの 3 本のあいだの、再現率の標準偏差と、件数の最大 ÷ 最小（`p2f:spread`）。
- 取りこぼしの原因の内訳、概念あたりの MeSH・フリーワードの語数、概念が 1 個だけの実行の数（`p2f:diagnose`）。
- 終わり方の内訳: 提出まで到達・打ち切り・エラーの数、関数の引数が読めなかった応答の数、空の応答の数、再試行の回数。
- 費用: 1 本あたりの入力・出力・推論のトークン数、応答の回数、所要時間、道具の呼び出し回数。中央値と最大値。金額は、OpenRouter が応答ごとに返す費用の合計を記録する（この計画には単価を書かない）。
- 実際に応答した提供元と、応答の `model`。
- ティア別（CC BY 5 件・CC BY-NC 15 件）と、検索日の新旧別の値。

## 5. 結果の読み方（実行前に固定）

採否の判定はしない。次の区分で読み、結果を見たあとで区分の線を動かさない。小さい実験の運用上の基準で、統計的な確証とは区別する。

**主な問い: Gemini 3.8 Flash・high の 1 本との差**（v1q27 − v1g38h、v1glm − v1g38h の平均再現率。モデルごとに読む）

| 区分 | 条件 | 読み方 |
|---|---|---|
| 並ぶ | 差が −0.03 より大きく、信頼区間が 0 をまたぐ | 公開モデルでも同じ水準の式が作れる候補として、開発群全体で確かめる価値がある |
| 下回る | 差が −0.03 以下で、信頼区間の上限が 0 を下回る | この設定では代わりにならない。Haiku 4.5・Haiku 5.5 のどちらに近いかを書く |
| 上回る | 差が +0.03 以上で、信頼区間の下限が 0 を上回る | 開発群全体で確かめる |
| どちらとも言えない | 上のどれでもない | 20 件 × 3 本では決められない。広げるかを依頼者に確認する |

0.03 は第 4・第 5 ラウンドと同じ線である。

**束ねる上積み**（v4q27 − v1q27、v4glm − v1glm）は、plan-round4.md §5 の 3 区分（束ねる価値がある／1 本で足りる可能性がある／どちらとも言えない）をそのまま使う。

**件数**は、区分とは別に、v1g38h に対する件数の比の中央値と、1 万件・5 万件を超えた実行の数を必ず書く。再現率が並んでも、件数が 2 倍を超えていれば、そのことを区分の横に書く。

**道具を使う作業が成り立つか**は、区分を置かずに数で書く。ただし、提出まで到達しなかった実行が 60 本中 6 本（1 割）を超えたモデルは、平均再現率の区分の横に「失敗による低下を含む」と書き、提出できた実行だけの平均再現率を参考として並べる（主な数字は、失敗を 0 として数えたほうのままにする）。

**このラウンドの結果で決めないこと**

- 製品の既定モデルや、製品で勧めるモデル。固定小集合 20 件は、手順書の選別に繰り返し使った集合である。
- 「公開モデルは使える／使えない」という一般的な結論。試すのは 2 つのモデル、1 つの提供元、1 つの推論の設定だけである。

## 6. 進め方

1. **OpenRouter 用の実行役を足す**（コードの変更）。いまの実行役は Gemini API 専用で、OpenRouter には送れない。製品側の `OpenRouterProvider.ts` と、tiab-review-plugin の実験用クライアントは、どちらも 1 回の質問と応答だけの作りで、関数呼び出しの往復には使えない。
   - `geminiRun.ts` と同じ流れの実行役を、OpenAI 互換の形式で書く（`openrouterRun.ts`、コマンドは `p2f:openrouter`）。共通にできる部分（関数の中身の実行、済んだ実行を飛ばして続きから流す処理、記録の書き方）は `geminiRun.ts` と共有し、Gemini 側の要求は 1 バイトも変えない。
   - 版の定義（`conditions.ts`）に、実行役の種類 `openrouter-api` と、提供元を固定する項目を足す。モデル ID の検査は、この実行役のときだけ `/` を含む ID を通す。推論の強さは #227 の項目をそのまま使う。
   - 提供元の固定は、tiab の実験用クライアントのやり方を使う（提供元を 1 つ指定し、ほかへの切り替えを禁じる。切り替わるくらいならエラーにする）。
   - 推論の内容を次の要求に返す必要があるモデルに備えて、応答のメッセージを丸ごと会話に戻す（Gemini の署名と同じ扱い）。テストで固定する。
   - 関数の引数は文字列で届くので、読めなかったときは道具を動かさず「引数が読めませんでした」と返して続けさせ、回数を記録する。
   - 実行ごとの記録に、応答した提供元、応答の `model`、推論のトークン数、OpenRouter が返した費用を残す。
   - 再試行は `geminiRun.ts` と同じ（429 と 5xx だけ、間隔を空けて最大 6 回、要求ごとに 120 秒で打ち切り）。HTTP 200 で本文がエラーの応答も失敗として再試行する。キーは記録・ログ・エラー文から伏せる。
   - キーは `OPENROUTER_API_KEY`。このリポジトリの `.env` には無いので、tiab-review-plugin の `.env` を実行時に読ませる（複製しない）。
   - 実装は commander に乗せ、レビューを通してからマージする。
2. **版を用意する**: `harness/` に v1q27・v1glm（手順書は v1 の写し。`conditions.json` にモデル・提供元・推論の強さ）と、v4q27・v4glm（`combine.from`、`k: 3`）を置く。手順書の語の重なり検査を通す。
3. **動作確認**: モデルごとに、動作確認用 5 件のうち 1 件 × 1 本を、別のフォルダで動かす（計 2 実行）。次を確かめる。この 2 本は採点に入れない。
   - 応答の `model` と提供元が指定どおりであること、推論のトークン数が 0 でないこと。
   - 提出まで到達すること。関数の引数が毎回読めること。推論の返し方に関するエラー（HTTP 400）が出ないこと。
   - GLM-5.3 の提供元を決める。まず開発元の Z.AI（fp8）で動かし、関数呼び出しか推論の指定が通らなければ、fp8 の別の提供元に替えて同じ確認をやり直す。決めた提供元は版の定義に書き、本番の途中で変えない。
   - 1 回の応答が、要求の制限時間（120 秒）に収まること。収まらなければ、本番の前に制限時間を延ばす。（2026-10-08 追記: Qwen3.8 27B の動作確認で、式の全文を書く応答が 120 秒に 2 回当たり、3 回目に約 110 秒で通った。OpenRouter の実行役の制限時間を 300 秒に延ばした。Gemini の実行役は 120 秒のまま）
   - 1 本あたりのトークン数と費用。見積もり（§7）の 3 倍を超えたら、本番の前に依頼者へ知らせる。
   - 1 本あたりの所要時間。60 本で半日を超える見込みなら、本番の前に依頼者へ知らせる（tiab の実験では、Qwen3.8 27B の推論ありが遅すぎて中断した）。
4. **本番の生成**: `p2f:openrouter` で `--version v1q27 --subset fixed --runs-per-review 3`、続けて v1glm。2 つのモデルを同時には流さない（NCBI のレート上限を 1 プロセスの中で守るため。plan.md §9）。並行数は 4 から始め、429 が出たら下げる。第 5 ラウンドの本番、ほかの実 API の計測、E2E とも同時に流さない。落ちたら同じコマンドで続きから流す（済んだ実行は飛ばし、エラーの実行だけ作り直す）。作り直した数を記録する。
5. **束ねる・採点する**: `p2f:combine` で v4q27・v4glm を作り、`p2f:score` で 4 つの版を同じ日に採点する。生成した実行の数（各 60）と採点できた数、束ねた式の数（各 20）を突き合わせる。
6. **比べる**: §4 の表の組を `p2f:compare` で出す（実行数の違う組は `--candidate-runs-per-review`）。`p2f:diagnose` と `p2f:spread` を v1q27・v1glm に、`p2f:spread` を v4q27・v4glm にかける。
7. **記録する**: log.md に「第 6 ラウンド」として、§3 の条件、§4 の表、§5 の区分、終わり方の内訳、費用、読み方の注意を書く。reports/ には集計値だけを置く（レビュー単位の行、式、PMID は置かない）。

モデル・提供元・推論の強さが指定どおりでなかった実行、通信の障害で道具が動かなかった実行だけを作り直す。打ち切り・未提出・関数の引数が壊れて進めなかった実行は作り直さず、失敗として数える。

集計のコードを足したり直したりする場合は、数値を報告する前にコードレビューを通す（plan.md §9）。

## 8. このラウンドで分かること・分からないこと

- 分かるのは、固定小集合 20 件・v1 の手順での、Qwen3.8 27B と GLM-5.3（どちらも OpenRouter 経由・推論 high・提供元 1 社）の 1 本と 3 本束ねの成績・件数・費用と、道具を使う作業を最後まで続けられる割合である。
- 差には、モデルの違い、推論の量の違い、API の形式の違い、提供元と量子化の違いが混ざる。どれが効いたかは分けられない。
- 手元の計算機で重みを動かしたときの成績は分からない。量子化を強くした版（4 ビットなど）の成績も分からない。
- 20 件 × 3 本では、差の信頼区間は広い（第 4 ラウンドの Sonnet と Opus の 1 本どうしで、+0.043 に対して 0.013〜0.081）。「どちらとも言えない」になる可能性を見込んでおく。
- 公開モデルの上位の版（Qwen3.8 2.4T-A95B、DeepSeek V4 Pro、Kimi K3）や、推論の強さを変えたときは分からない。
- 手順書 v1 は Haiku 4.5 の失敗を見て作ったものである。これらのモデル向けに直せば結果は変わりうる。
- 固定小集合は開発群の一部で、Cochrane レビューに偏る。開発群全体・検証群で同じ大きさになるかは分からない。
